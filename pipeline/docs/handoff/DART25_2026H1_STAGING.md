## 3. 정정 공시 처리

- **신규 수집:** 정정이 있는 5개 슬롯은 정정 반영본(최신 접수번호)으로 적재했다. 원 공시와 정정 공시 날짜는 슬롯 목록에 남겼다.
- **이미 적재한 슬롯에 정정이 나온 경우:** `replace_slot`을 쓴다.
  1. 그 슬롯의 API 사실값, 그 기업·연도의 계산 분기, 사실값 기반 지표를 이력 테이블(`financial_facts_history`, `financial_metric_values_history`)로 보관한다. 보관 시각, 새 접수번호, 사유를 함께 남긴다.
  2. 해당 슬롯만 교체하고, 그 기업·연도의 분기와 지표만 다시 만든다.
- **검증**
  - 같은 내용으로 다시 교체하면 변경 0이다.
  - 값 하나를 바꾼 가상 정정 공시를 넣었을 때:
    - 해당 기업·연도만 바뀌었다(사실값 241행·지표 50행 보관 후 재생성).
    - 다른 기업·연도는 불변이고, 순이익 변경만 Q1 누적·분기 지표에 반영됐다.
    - 재실행 시 변경 0, 중복 0이다.
  - 운영 사본 기반 회귀 테스트로도 고정했다(`tests/test_period_increment.py`).
- **MySQL:** 이력 테이블은 SQLite에만 있다(MySQL 동기화 대상 아님). 운영 반영 시 MySQL 쪽에서는 교체된 행이 `is_active=0`으로 남는다.

## 4. 부호 충돌 18건과 금융 비용 지표 60행 (2단계 대기)

| 대상 | 현재 처리 | 2단계 |
|---|---|---|
| 계산 분기 부호 충돌 18건(모두 CF) | 원값 차이를 저장하고 `sign_conflict_review` 표시. 자동 보정 안 함 | 원문 표시 부호와 표시 방식 변경 여부로 판정. 표시 부호 차이만 정렬 매니페스트에 추가 |
| 보류 분기 205건(태그 없음 115, 부호 충돌 52, 계정명 변경 38) | 생성하지 않음 | v10과 같은 원문 규칙으로 판정, 근거가 확인된 것만 생성 |
| 금융 비용 지표 60행 | 원값 그대로 `review_required`(표준화 기록 `unverified`) | v9 기준(소계 관계 또는 기준 줄 표시)으로 판정. 순환입은 음수로 둠 |
| API 3개월값 ≠ 누적 차이(2026 신규 34건) | 감사 정보 항목 | 원문으로 확인 |

2단계 도구는 준비했다: `python -m src.quality.increment_evidence --db … --collection … --year 2026 [--write]`
- 원문을 판정 단계에 등록하고 세 가지 판정을 한 번에 실행한다.
- `--write`일 때만 정확한 값으로 키를 단 항목을 매니페스트에 추가한다. 2023~2025 결과는 바뀌지 않는다.

## 5. 원본 XML 확보·출처 연결

- **현재:** 미확보. 원문 서비스가 점검 중이다.
- **수집 대상:** 슬롯별 최신 유효 공시 50건. 접수번호와 저장 위치는 `slots_2026h1.json`에 있다.
- **다운로드 방식:** `period_increment_pipeline --download-xml`

  - 오류 응답은 사유를 그대로 보고하고 저장하지 않는다.
- **출처 연결:** 재무 API 사실값의 `rcept_no`가 최신 유효 공시와 50/50 일치한다. 원문을 받으면 같은 접수번호로 바로 연결된다.

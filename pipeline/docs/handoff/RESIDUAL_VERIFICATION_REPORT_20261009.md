## 3. 판정 방법

부호 판정에 `abs()`를 쓰지 않았다. 각 누적값이 공시 원문에서 어떻게 **표시**됐는지를 대조했다.

1. **공시 XML 표시 부호**
   - 같은 보고서의 재무제표 표에서 같은 계정명·금액(단위 환산)을 찾아 괄호 여부를 읽었다.
   - 두 누적값의 표시가 같으면(둘 다 괄호 또는 둘 다 괄호 없음) API 부호만 뒤집힌 것이다. 이 경우를 **표시 부호 차이**로 판정했다.
   - 표시가 다르면 손익이 실제로 바뀐 것이다(이익↔손실, 환입↔전입). 이 경우를 **실제 부호 반전**으로 판정했다.
2. **다음 연도 비교 수치**
   - 다음 해 같은 보고서의 전기 열(`frmtrm_amount`, 손익 분·반기는 `frmtrm_add_amount`)을 썼다.
   - 이 값은 두 기간을 하나의 부호 규칙과 계정으로 다시 보여 준다.
   - 두 값이 모두 저장값과 절댓값이 같을 때만 근거로 인정했다.
3. **계정 연결 기준**
   - 이름이 바뀌었거나 태그가 다른 계정은 다음 두 경우에만 같은 계정으로 연결했다.
     - 다음 연도 비교 수치가 같은 공식 태그(`ifrs-full_`·`ifrs_`·`dart_`)로 두 값을 함께 보여 줄 때
     - 같은 표의 같은 행일 때
   - 이름이 비슷하다는 이유만으로는 연결하지 않았다.
4. **재작성 처리**
   - 다음 연도 비교 수치가 저장값과 다르면 회계정책 변경 등으로 재작성된 것이다.
   - 이 경우 저장값을 오류로 보지 않고 검토 필요로 분류했다. 단, E는 예외다(5-2절).

## 5. 재발 방지 (파이프라인 연결)

## 7. 운영 반영 (승인 후에만)

1. **반영 전 운영본의 상태**
   - 재생성 시 보정 10건만 "저장값 = 이전 오류값, 재생성 = 보정값"으로 다르게 나온다. 테스트는 이 경우만 허용한다.
   - 잔여 보정 파이프라인(`apply_residual_fixes`)은 재생성 불일치가 있으면 중단한다. 따라서 v8을 반영하기 전에는 운영본에 실행하지 않는다. 테스트는 사본에 v8을 먼저 적용한 뒤 실행한다.
2. **절차:** 운영 백업 → `residual_v8_r2` 교체 → 테스트·감사 → MySQL 적재(`--defer-promotion`) → 검증 → 승격. 제안 버전명: `2026-10-09-dart25-residual-v8`
3. **KPI v7은 계속 보류한다.**
   - 위 회귀 결과대로 v8은 일반 KPI 값을 바꾸지 않는다.
   - KPI v7을 반영할 때는 그 시점의 운영본에서 KPI를 다시 생성한다.

# 은행 신용손실비용 부호 불일치 조사 (읽기 전용)

- 작성일: 2026-10-09
- 대상: 금융 5개사(신한·하나·KB·카카오뱅크·우리), 2023~2025, 지표 `CREDIT_LOSS_EXPENSE`
- 운영본: SQLite·MySQL current `2026-10-09-dart25-residual-v8` (`financial.db` `72a77cb9…`). 이번 조사에서 변경하지 않았다.
- 근거 표(60개 누적 기간): `backups/quality/20261009_creditloss_sign/credit_loss_sign_evidence.csv` (`SHA256SUMS`)

## 1. 결론

1. **60개 누적 기간(5개사 × 12기간)은 모두 실제 비용(신용손실충당금 순전입)이다.** 환입이 비용보다 컸던 기간은 없다.
2. **금액 크기는 모두 맞다.** 120개 지표 행(누적 60·분기 60)의 절댓값이 근거와 일치한다.
   - 분기값도 표준화한 누적값의 차이와 크기가 모두 같다(차이 0건).
3. **문제는 부호뿐이다.** 120행 중 28행이 음수로 저장돼 있다(신한 14, 우리 8, 하나 6).
   - 음수 행은 환입이 아니라, 그 공시의 API(XBRL)가 비용을 음수로 보낸 것이다.
   - 이 때문에 같은 회사·같은 연도 안에서도 분기 부호가 섞인 경우가 4개 있다(신한 2024, 하나 2023, 우리 2023·2024).
4. **현재 값의 부호로는 회사 간·기간 간 비교를 할 수 없다.** 부호를 표준화하면 5개사 모두 "양수 = 비용"으로 같은 의미가 된다.
5. **수정 대상은 지표 계층의 부호 표현이다.** 원천 사실값(API 원값)은 공시 그대로 보존해야 한다.
   - 이 지표를 입력으로 쓰는 파생 지표·KPI는 현재 없다.
   - 다만 분석기는 값을 그대로 LLM에 넘기므로 증감 해석이 뒤집힐 수 있다.

## 2. 판정 방법

부호만 보고 판단하지 않았다. 다음 근거를 회사·기간별로 대조했다.

| 근거 | 내용 | 적용 범위 |
|---|---|---|
| ① 소계 산술 | 원문 손익계산서에서 "앞 소계 − 신용손실 = 뒤 소계"가 성립하고 앞 소계가 더 크면 차감되는 비용 | 하나 12기간(총영업이익 → 순영업이익), KB 11기간(신용손실충당금 반영전 영업이익 → 영업이익) |
| ② 기준 비용 줄과 표시 방식 | 같은 표의 일반관리비와 같은 방식(둘 다 괄호 또는 둘 다 괄호 없음)으로 표시되면 비용 | 신한·우리(둘 다 괄호), 카카오뱅크(둘 다 괄호 없음) |
| ③ 계정명 | "전입액", "손상차손", "(전)환입액·환입(전입)" 줄의 괄호 표시 = 전입 | 전체(보조) |
| ④ 누적 단조 증가 | 같은 해 \|Q1\| < \|H1\| < \|Q3\| < \|FY\|이면 어느 분기에도 순환입이 없음 | 15개 은행-연도 모두 성립 |

- 예외 1건: 하나 2025 Q1 원문은 신용손실(297,226)을 괄호 없이, 일반관리비는 괄호로 표시했다.
  - 같은 표의 "총영업이익 3,410,124 − 297,226 = 순영업이익 3,112,898"로 비용임이 확정된다.
  - 따라서 ②만 쓰는 규칙은 불완전하고, ①을 우선해야 한다.
- 카카오뱅크 2023 Q3·FY에서는 API의 일반관리비만 음수였다(신용손실은 양수). XML은 둘 다 괄호 없이 표시한다. 기준선 쪽 API 부호도 믿을 수 없다는 뜻이다.

## 5. 권장 부호 정책

**원본 부호와 분석용 표준 부호를 계층으로 분리한다.**

| 계층 | 값 | 부호 규칙 |
|---|---|---|
| 원천 `financial_facts.raw_value` / `normalized_value` | 공시·API 값 | 바꾸지 않는다 |
| 지표 `financial_metric_values.value` (비용형 지표) | 분석용 표준값 | **양수 = 비용(순전입), 음수 = 순환입(이익)** |
| 지표 `source_values` | 근거 기록 | `presented_value`(원값), `sign_basis`(subtotal / reference_line / label), `sign_standardized`(true/false) |

규칙:
1. 표준 부호는 **근거로 정한다.** `abs()`를 일괄 적용하지 않는다. 우선순위는 ① 소계 산술, ② 같은 표의 기준 비용 줄(일반관리비) 표시 방식, ③ 계정명 순이다.
2. 근거가 없거나 서로 엇갈리면 원값을 유지하고 `review_required`로 둔다.
3. 분기값은 **표준화한 누적값의 차이**로 만든다. 저장된 분기값을 단순히 뒤집지 않는다.
   - 이렇게 하면 같은 해 안에서 부호 관행이 바뀌어도 분기 합이 FY와 맞는다.
4. 실제 순환입 기간이 나오면 표준값은 음수로 둔다. 근거 ①에서 "앞 소계 + 신용손실 = 뒤 소계"인 경우다.
5. 같은 정책을 `INTEREST_EXPENSE`, `FEE_COMMISSION_EXPENSE`에도 적용한다. 순이익류 지표에는 적용하지 않는다(부호가 의미 자체다).
6. 지표 정의(`financial_metric_definitions`)에 `sign_convention = 'expense_positive'`를 명시한다. 이 컬럼은 반영할 때 추가한다.

## 6. 수정 대상과 반영 방법(제안, 미실행)

| 대상 | 건수 | 방법 |
|---|---:|---|
| `CREDIT_LOSS_EXPENSE` 음수 누적·연간 행 | 14 | 표준 부호로 바꾸고 원값·근거를 `source_values`에 기록 |
| `CREDIT_LOSS_EXPENSE` 음수 분기 행 | 14 | 표준 누적값의 차이로 다시 계산(크기는 현재와 같음) |
| 원천·계산 사실값 | 0 | 변경 없음 |
| 파생 지표·KPI | 0 | 변경 없음 |

- **구현 위치(반영 시)**
  - 지표 생성(`_fact_metric_rows`, 문서 추출·분기 도출 단계)에 비용형 지표의 부호 표준화 단계를 추가한다.
  - 근거 판정은 `src/quality/residual_verification.py`의 원문 표시·소계 확인 함수를 재사용한다.
  - 판정 결과는 이번 근거 표처럼 고정 매니페스트로 둔다. 그래야 재빌드·재수집에도 같은 결과가 나온다.
  - 감사의 "DIRECT 지표 = 원천 사실값" 검사는 `sign_standardized` 행에 한해 |값| 일치와 근거 존재를 확인하도록 바꾼다.
- **staging:** 이번에는 만들지 않았다. 부호 정책은 백엔드가 받는 값의 의미를 바꾸는 계약 변경이므로, 정책 승인 후 staging에서 구현·검증하는 순서가 맞다.
  - 대신 표준화 결과의 일관성은 읽기 전용으로 검증했다(3절: 크기 차이 0, 누적 단조 증가, 분기 = 누적 차이).
- **백엔드 합의 필요:** 분석기는 반영 후 값을 그대로 써도 된다. 반영 전에는 6절 주의사항에 따라 크기와 계정명으로 해석해야 한다.

## 7. 백엔드 주의사항 (반영 전까지)

- `CREDIT_LOSS_EXPENSE`의 부호는 비용/환입을 뜻하지 않는다. 2023~2025년 5개사 모든 기간이 비용이다.
- 증감·순위·평균은 **절댓값으로 계산**한다. 단, 이는 이번 조사 범위(2023~2025, 5개사)에서 검증된 경우에만 해당한다. 새 기간은 근거 확인 전까지 같은 가정을 쓰지 않는다.
- 같은 내용을 `docs/handoff/DATA_DICTIONARY.md` 8절과 `docs/handoff/BACKEND_KPI_HANDOFF.md` 6절에 기록했다.
